# 故障模式目录

循环实际失效的各种方式——以及优秀的设计如何缓解这些问题。在调试行为异常的循环或编写新模式时，请参考本文档。

## 分类

| 严重级别 | 含义 |
|----------|---------|
| **S1 — 烦人** | 浪费时间/令牌，对用户无伤害 |
| **S2 — 有害** | 错误的代码被合并、糟糕的工单、警报疲劳 |
| **S3 — 严重** | 安全问题、数据丢失、生产事故 |

---

## 无限修复循环

**症状**：同一个 PR 或 CI 任务被自动修复尝试 5 次以上；始终无法收敛。

**严重级别**：S2

**原因**：
- 验证器太弱，或与实施者使用同一会话
- 根本原因误诊（只修症状）
- 将不稳定测试误判为回归

**缓解措施**：
- 设置尝试次数硬上限（例如 3 次）→ 升级给人工处理
- 使用独立的验证器模型 / 更高的推理强度
- 在分诊中分类不稳定测试；隔离而非修改代码
- 在状态文件中记录尝试次数

---

## 状态腐化

**症状**：`STATE.md` 引用了已合并的 PR、已关闭的工单或过时的分支。

**严重级别**：S1 → S2（循环基于幽灵数据行动）

**原因**：
- 运行结束时没有清理步骤
- 开始时未读取状态文件
- 多个循环写入同一文件且无 Schema

**缓解措施**：
- 每次运行都清理已关闭/已合并的项目
- 添加 `上次运行` 时间戳 + 对照实时 API 验证 ID
- 每个循环模式使用一个状态文件，或使用清晰的分区

---

## 验证器走过场

**症状**：验证器“批准”了，但 CI 中测试失败，或审查发现明显错误。

**严重级别**：S2

**原因**：
- 验证器提示词过于模糊（“看起来不错”）
- 验证器不运行测试
- 与实施者使用相同模型、相同上下文

**缓解措施**：
- 验证器必须运行测试/代码检查命令并报告输出
- 使用不同的指令：“找出拒绝的理由”
- 无人值守循环使用更强的验证器模型

---

## 通知疲劳

**症状**：Slack/邮件每 5 分钟响一次；团队直接屏蔽机器人。

**严重级别**：S1 → S2（真正的升级被忽略）

**原因**：
- 每次运行都通知，而非每个*可操作*的发现
- 分诊技能中“高优先级”的门槛过低

**缓解措施**：
- 仅在需要人工决策时通知
- 仅报告型循环使用摘要模式
- 收紧分诊“高优先级”规则

---

## 令牌消耗

**症状**：账单飙升；循环在空或嘈杂的分诊上运行完整的子代理链。

**严重级别**：S1

**原因**：
- 子代理过重且执行频率低于一分钟
- 监视列表为空时没有提前退出
- 在临时 API 错误时重试整个流水线

**缓解措施**：
- 先做更便宜的分诊通道；仅对可操作项目启动子代理
- 无内容可监视时执行 `scheduler_delete`
- 设置每日令牌预算 → 暂停循环
- 参见 [operating-loops.md](./operating-loops.md)

---

## 越界操作（错误范围）

**症状**：循环重构无关模块、“修复”设计问题，或触碰黑名单路径。

**严重级别**：S2 → S3

**原因**：
- 最小修复技能过于宽松
- 没有路径白名单/黑名单
- 分诊将架构工作标记为“高优先级”

**缓解措施**：
- 在技能中强制执行 [safety.md](./safety.md) 黑名单
- “最小可能的差异” + 验证器检查被修改的文件
- 分诊技能：仅做信号标记，不做发明创造

---

## 理解债务螺旋

**症状**：速度上去了，但没人能解释最近的变更；审查变成橡皮图章。

**严重级别**：S2（长期）

**原因**：
- 人工不再阅读循环输出
- 白名单不断扩大并自动合并
- 没有每周人工对循环操作的综合总结

**缓解措施**：
- 非平凡 PR 必须人工审查
- 负责人每周阅读“循环摘要”
- 将自动合并限制在真正微不足道的路径

---

## 认知放弃

**症状**：“循环会处理的”——对正确性或设计没有任何意见。

**严重级别**：S2（文化层面）

**原因**：
- 循环成功指标 = 数量，而非质量
- 中等风险工作没有人工关卡

**缓解措施**：
- 每个模式都设置明确的人工关卡
- 成功指标：在保持质量门槛的前提下节省的时间
- Osmani 的话：“像打算长期留任的工程师一样去构建”

---

## 并行冲突

**症状**：两个子代理编辑同一文件；合并冲突；状态损坏。

**严重级别**：S2

**原因**：
- 没有工作树隔离
- 两个循环在无协调的情况下操作同一 PR

**缓解措施**：
- 所有代码编辑子代理使用 `isolation: worktree`
- 在状态中加锁或排队：“PR #1234 — 工作树进行中”

---

## 升级失败

**症状**：循环卡在重试中；人工从未被通知。

**严重级别**：S2

**原因**：
- 未实现最大尝试次数
- 升级仅写入无人阅读的状态

**缓解措施**：
- 升级时通过连接器发送通知（Slack、Linear 评论）
- 在 STATE.md 中设置 `高优先级（等待人工）` 分区
- 该分区中的项目超过 24 小时则发出警报
