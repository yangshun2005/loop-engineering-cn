# 生产环境中的循环运行

运行循环属于运维工作。本文档涵盖成本、日志、指标，以及何时暂停或终止循环。

## Token 与成本预算

在调度前进行估算：

```bash
npx @cobusgreyling/loop-cost --pattern <id> --cadence <interval> --level L1
npx @cobusgreyling/loop-init . --pattern <id>   # 生成 loop-budget.md + loop-run-log.md + loop-budget 技能
```

`loop-audit` 会对成本可观测性进行评分，并在预算、运行日志和 LOOP.md 预算部分存在之前，将 L3 级别设为上限。

粗略规划因素：

| 因素 | 影响 |
|--------|--------|
| 调度频率 | 线性倍数（5分钟 vs 1天 = 每天运行次数相差 288 倍） |
| 每次运行的子代理数 | 每个子代理 = 完整的模型 + 工具往返 |
| 上下文大小 | 大型仓库 + 完整 CI 日志 = 高成本的分诊 |
| 验证器模型 | 验证器使用更强的模型 = 对无人值守场景值得投入 |

### 示例估算（数量级）

假设每次轻量分诊运行约消耗 5 万 tokens，每次带实施器和验证器的运行约消耗 20 万 tokens：

| 循环 | 调度频率 | 每天运行次数 | 粗略每日 tokens |
|------|---------|----------|-------------------|
| 每日分诊（仅报告） | 1天 | 1 | ~5万 |
| CI 清扫器（轻量） | 15分钟 | 96 | ~500万（如果每次运行都是全量 — **应避免**） |
| PR 守护器 | 5分钟 | 288 | 高 — 使用提前退出 |

**最佳实践**：分诊阶段成本低；仅在状态显示有可操作事项时才生成子代理。监视列表为空 → 在 5 千 tokens 以内退出。

### 预算规则

```markdown
## 循环预算 — 项目 X
- 每日最大 tokens：2M（根据你的计划调整）
- 超出时：暂停调度器，通知人工
- 每次运行最大子代理生成数：3
```

在技能或调度器提示中编码：“如果没有高优先级事项，立即退出。”

## 记录每次运行

最小日志条目（追加到 `loop-run-log.md` 或结构化 JSON）：

```json
{
  "run_id": "2026-06-09T08:15:00Z",
  "pattern": "daily-triage",
  "duration_s": 45,
  "items_found": 4,
  "actions_taken": 1,
  "escalations": 0,
  "tokens_estimate": 52000,
  "outcome": "success"
}
```

`STATE.md` 底部的人类可读替代格式：

```markdown
---
运行日志：2026-06-09 08:15 | 4 项发现 | 1 个工作树已打开 | 0 次升级
```

## 何时减速

- 周中 Token 预算已使用超过 80%
- 分诊误报率超过 30%
- 同一事项在 48 小时内被升级 2 次以上
- 重大发布周 — 暂停自动修复循环，仅报告

## 何时暂停

- 生产事故进行中（循环可能与热修复冲突）
- 破坏性 Schema 迁移正在进行
- 关键人工审核人不在岗且自动合并已启用（不要这样做）

## 何时终止循环

- 来自 [failure-modes.md](./failure-modes.md) 的持续 S2 故障
- 连续两周成本大于价值
- 团队静默所有通知
- 模式已被事件驱动替代方案取代（例如仅使用 CI Action）

**终止检查清单**：
1. `scheduler_delete` / 禁用自动化 / 移除 Action
2. 归档状态文件并标记 `status: retired`
3. 在 `stories/` 中进行事后复盘（可选但很有价值）

## 升级路径

```
仅报告（L1）→ 1–2 周稳定分诊
       ↓
小型自动修复（L2）→ 验证器 + 工作树 + 最大尝试次数
       ↓
连接器（L2+）→ 自动更新 PR/工单
       ↓
无人值守（L3）→ 仅在具有黑名单、预算、指标、人工门禁的情况下
```

对于生产仓库上的新模式，切勿跳过 L1 级别。
