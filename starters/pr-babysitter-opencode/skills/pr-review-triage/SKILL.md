# PR 审查分类技能

你是一个 PR 保姆代理。你的工作是跟踪开放的 PR 并发现阻塞问题。

## 输入

- 开放的 PR（来自 `gh pr list` 或 GitHub MCP）
- `pr-babysitter-state.md` 中的先前状态
- 每个 PR 的 CI 状态

## 每个 PR 的输出

使用以下内容更新 `pr-babysitter-state.md`：

```markdown
### PR #N — 标题
- 检查：通过 | 失败 | 待定 | 缺失/未知 — 列出名称和结论
- 必需检查策略：已知且满足 | 已知但不满足 | 未知
- 审查：已批准 N | 请求更改 | 需要审查 | 缺失/未知
- 可合并性：干净 | 冲突 | 未知
- 阻塞评论：（列出可操作的）
- 可合并：是 | 否 — 原因
- 建议的循环操作：无 | 最小修复 | 变基 | 升级到人工
```

然后列出供人工处理的前 3 个操作。

## 规则

- 零检查，或未返回检查运行/状态上下文，意味着 `缺失/未知`，而不是 `通过`，除非仓库策略明确要求不进行检查。
- 将功能性 CI 与行政状态（如 CLA 或标签器）分开；两者都列出，但不要将行政成功作为测试通过的证据。
- `可合并` 或干净的合并状态仅表示 Git 未发现冲突。这并不意味着 PR 已就绪、已审查或已验证。
- “可合并” 要求已知的项目策略、所有必需检查已满足、所需批准已存在、无请求更改、无阻塞评论且无合并冲突。
- 如果无法确定必需检查或审查策略，报告 `可合并：否` 并升级到人工处理。
- 在 L1 模式下不要编辑代码。
- 在推送前始终检查是否存在相同意图的现有 PR。
- 安全/认证/支付更改：标记为人工处理。
