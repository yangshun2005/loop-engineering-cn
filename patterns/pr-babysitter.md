# PR 保姆循环

**目标**：减少人工在拉取请求的审查、CI、变基和合并上所花费的时间，同时将判断权保留在人工手中。

## 调度

**推荐**：
- `/loop 5m /pr-babysit check`（Grok TUI）
- 在其他环境中，等效的定时任务或 GitHub Action（工作时间内每 5–15 分钟一次很常见）。

许多团队在活跃审查期间运行更快的“监视器”循环（2–5 分钟），并在夜间运行较慢的清扫器。

## 所需技能

- `pr-review-triage` — 理解你项目的审查规范、必需的检查，以及“准备合并”意味着什么。
- `minimal-fix` — 生成解决特定审查者评论或 CI 失败的最小变更。
- `rebase-and-clean` — 适用于你仓库的安全变基 + 冲突解决模式。

## 状态

维护一个小的 `pr-babysitter-state.md`（或 Linear 看板 / GitHub 项目视图），包含：

- 被监视的 PR + 当前状态
- 上次采取的操作 + 结果
- 覆盖循环的人工决策

状态条目示例：
```markdown
- #1234 (feat/auth-refresh)
  检查：通过（单元测试，lint）
  必需检查策略：已知且已满足
  审查：@reviewer 请求了变更
  可合并性：干净
  准备合并：否 — 已请求变更
  上次操作：循环为评论 X 提出了最小差异
  人工决策：批准了差异，要求再增加一个测试
```

## 循环运行方式（典型周期）

1. 发现团队编写的开放 PR（或用户关心的所有 PR）。
2. 对于每个 PR：
   - 运行分类技能。
   - 将检查分类为通过、失败、待定或缺失/未知；记录仓库的必需检查策略是否已知。
   - 如果检查失败 → 生成带有 `minimal-fix` 技能的子代理来处理失败。如果待定 → 等待。如果缺失/未知 → 建立仓库策略或升级处理，而不是假设为绿色。
   - 如果存在审查评论且可操作 → 提出最小补丁。
   - 如果准备就绪（已知策略已满足、必需的批准已存在、没有请求变更或阻塞评论，且没有合并冲突） → 添加“准备合并”标签或通知人工。
3. 对于闲置过久的 PR → 建议关闭或移交。
4. 将简洁的更新写回 PR 和状态。
5. 任何模糊或高风险的内容 → 附上上下文向人工呈现。

## 断路器

这是一个可修复（L2）模式，因此 `loop-init` 会自动为其搭建 `loop-guard` 技能和种子化的 `loop-ledger.json`。在对被监视的 PR 进行每次重试尝试之前，运行断路器：

```bash
npx @cobusgreyling/loop-context --check --ledger loop-ledger.json \
  --budget-from-pattern pr-babysitter --budget-level L2
```

非零退出码表示相同的失败重复发生或尝试上限已达成 — 停止并升级给人工处理，而不是继续在 PR 上评论/重试。参见 [docs/safety.md](../docs/safety.md)。

## 验证策略

- 绝不让实现者子代理将自己的工作标记为“完成”。
- 使用独立的验证者子代理（制造者/检查者）（或更高投入的更强模型），必须明确确认：
  - 变更解决了评论/失败。
  - 没有触及无关文件。
  - 测试/lint 在工作树中仍然通过。
- 循环仅提出建议；实际合并由人工（或针对非常安全情况的显式“自动合并”白名单）执行。

## 人工交接点

- 高风险重构
- 涉及安全、支付、认证或核心基础设施的变更
- 当循环在同一 PR 上提出 > N 次修复而没有进展时
- 当状态文件显示同一 PR 连续数天出现时

## 工具特定说明

**Grok Build TUI**：
- `pr-babysit` 技能（如果已安装）正是为此设计的。
- 使用 `/loop 5m /pr-babysit check` 运行。
- 对任何修复尝试使用工作树隔离。
- 当监视列表为空时，该技能可以自行调用 `scheduler_delete`。

**Claude Code**：
- Boris Cherny 已公开描述过运行非常类似的 `/loop 5m /babysit` 流程。
- 与 `/goal` 结合使用，实现“持续处理此 PR，直到 CI 变绿且没有阻塞评论”。

**通用**：
- 将状态文件暴露在仓库或共享文档中，以便整个团队可以看到循环在做什么。
- 让循环在 PR 上的评论有清晰的签名（例如“🤖 Loop Engineering — PR 保姆”）。

## 失败模式与缓解措施

- **循环提出错误的修复** → 强大的验证者子代理（制造者/检查者）+ 对任何超出琐碎范围的内容进行人工审查把关。
- **缺失的检查看起来是绿色的** → 将零返回的检查表示为 `缺失/未知`；在仓库策略已知且所有审查/检查门已满足之前，干净/可合并的 PR 不算准备就绪。
- **无限变基循环** → 限制每个 PR 的自动变基尝试次数。
- **状态过期** → 循环应在每次运行时清理已关闭/已合并的 PR。
- **通知疲劳** → 使用选择性通知（仅在真正需要人工操作时）。

## 成本概况

| 场景 | 每次运行的令牌数 | 备注 |
|----------|------------|-------|
| 无操作（空监视列表） | ~3k | **目标是大多数运行** — 提前退出 |
| 分类遍历 | ~80k | PR + CI 状态扫描 |
| 修复尝试（L2） | ~250k | 工作树 + 最小修复 + 验证者 |

**节奏**：5 分钟–15 分钟 · **层级**：高 · **建议每日上限**：200 万令牌 · **需要提前退出**

```bash
npx @cobusgreyling/loop-cost --pattern pr-babysitter --cadence 10m --level L1 --conservative
```

没有提前退出的高节奏会快速消耗令牌。使用 `loop-budget` 技能 + `loop-run-log.md`。

## 成功指标

- 从“准备审查”到合并的平均时间（针对循环处理过的 PR）。
- 纯粹是“LGTM，循环处理了其余部分”的人工评论数量。
- Slack/Linear 中“你能变基吗？”或“CI 是红色的”消息的减少。

从一个团队或一个仓库开始。测量一周。然后扩展。
