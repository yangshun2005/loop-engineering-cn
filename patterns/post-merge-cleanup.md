# 合并后清理循环

**目标**：在合并到主分支后，清理后续工作——弃用项、待办事项、技术债务工单、过期的功能开关和文档缺口——而不阻塞合并本身。

## 调度

**推荐**：
- `/loop 1d` 或 `/loop 6h`（优先级低于 CI 清理循环）
- 通过 GitHub Webhook → Action 在合并事件时触发（事件驱动）
- 小型团队使用每周定时任务

在非工作时间或夜间运行，避免与活跃的开发循环竞争。

## 所需技能

- `post-merge-scan` — 读取最近的合并、差异摘要、关联工单；识别清理机会
- `minimal-fix` — 小型后续修复（删除死代码、更新弃用通知、修复文档中的失效链接）
- 项目约定技能 — 仓库中“清理”的含义

## 状态

`post-merge-state.md`：

```markdown
# 合并后清理

上次运行：2026-06-09 22:00 UTC

## 待清理项（来自最近的合并）
- [ ] PR #1245 已合并 — 移除 `legacyAuth` 开关（合并中标记了 TODO）
  来源：提交 abc1234，auth/handler.ts 第 42 行
  风险：低 | 工作量：小
- [ ] PR #1240 已合并 — 更新新端点的 API 文档
  风险：低 | 工作量：小

## 已完成（最近 14 天）
- PR #1230 — 移除了未使用的导入集群（PR #1248）

## 已推迟（需人工决策）
- PR #1238 — 大型重构已推迟；已创建工单 ENG-1001
```

## 循环运行方式（典型周期）

1. 列出自上次运行（或最近 N 天）以来合并到主分支的合并。
2. 对每次合并：扫描差异中的 TODO、弃用项、`// remove after`、功能开关、失效的文档链接。
3. 交叉引用关联的 Linear/GitHub Issue，查找明确的后续事项。
4. 确定优先级：小且低风险 → 在工作树中提出修复；大 → 创建工单并标记人工处理。
5. 验证者确认清理不会改变行为（有意删除除外）。
6. 打开小型 PR 或每天批量合并为一个“清理”PR。
7. 更新状态；清理已完成项。

## 断路器

这是一个可修复（L2）模式，因此 `loop-init` 会自动搭建 `loop-guard` 技能和预置的 `loop-ledger.json`。在每次对同一回归问题重试前运行断路器：

```bash
npx @cobusgreyling/loop-context --check --ledger loop-ledger.json \
  --budget-from-pattern post-merge-cleanup --budget-level L2
```

非零退出码表示相同失败已重复或尝试次数已达上限——停止并升级给人工处理。参见 [docs/safety.md](../docs/safety.md)。

## 验证策略

- 清理不得改变行为，除非是明确删除死代码路径。
- 验证者运行完整测试套件——出现回归立即交接。
- 涉及超过 10 个文件的清理 PR 未经人工批准不得自动合并。

## 人工交接点

- 需要设计讨论的架构性技术债务
- 影响生产配置的功能开关移除
- 有外部 API 使用方的弃用项
- 循环尝试两次仍未通过测试的任何清理项

## 失败模式与缓解措施

| 失败 | 缓解措施 |
|---------|------------|
| 过度激进删除 | 验证者 + “无行为变更”规则；大型差异需人工把关 |
| 遗漏合并 | 使用 GitHub API 合并列表，而非仅本地 git log |
| 每个 TODO 都产生噪音 | 仅处理有合并上下文或关联工单的 TODO |
| 与功能开发竞争 | 非高峰运行；限制每日自动 PR 数量（例如 2 个） |

## 成本概况

| 场景 | 每次运行 Token | 备注 |
|----------|------------|-------|
| 无操作 | ~5k | 没有需要扫描的近期合并 |
| 扫描 + 优先级排序 | ~40k | 合并列表 + TODO 扫描 |
| 小型修复（L2） | ~150k | 工作树 + 验证者 |

**节奏**：1d–6h · **层级**：低 · **建议每日上限**：200k tokens

```bash
npx @cobusgreyling/loop-cost --pattern post-merge-cleanup --cadence 1d --level L1
```

非高峰运行。在 `loop-budget.md` 中限制每日自动 PR 数量。

## 成功指标

- “合并后忘记移除 X”事件减少
- 未关闭的合并后清理项的存在时间
- 无需审查意见即合并的清理 PR 百分比

风险低于 CI 清理循环——在每日分类稳定后，是很好的第二个循环。
