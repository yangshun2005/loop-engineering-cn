# 每日分类循环

**目标**：以一份按优先级排序、可操作的事项清单开启每一天（或每个活跃时段）——无需手动检查 CI、Issue、PR 和聊天记录。

## 调度

**推荐**：
- 使用 `/loop 1d` 进行晨间分类（Grok、Claude Code）
- 在活跃冲刺期间使用 `/loop 2h` 获取更快的信号
- 对于没有 TUI 的团队，使用 GitHub Action 定时任务 `0 8 * * 1-5`

许多团队在启用自动操作之前，会先以仅报告模式（只报告，不自动修复）运行 1-2 周。

## 所需技能

- `loop-triage` — 读取 CI、Issue、提交、聊天记录；生成按优先级排序的发现结果（参见 `templates/SKILL.md.loop-triage`）
- `minimal-fix`（可选，第二阶段）— 为明显的失败起草小型修复方案
- 审查者子代理或技能（可选，第二阶段）— 验证提议的修复方案

## 状态

使用 `STATE.md`（或 Linear 看板视图）作为记忆主干：

```markdown
# 循环状态 — 项目 X

上次运行：2026-06-09 08:15 UTC

## 高优先级（循环正在处理或等待人工处理）
- [ ] #1241 — 认证流程中的不稳定测试（main 分支 CI 红色）
  循环操作：已打开工作树。已提出修复方案。等待人工 PR 审查。

## 观察列表
- PR #1238 已开启 4 天，无任何活动。

## 近期噪音（本次运行已忽略）
- Dependabot PR（独立自动化）
```

循环每次运行必须更新的字段：
- `上次运行` 时间戳
- 项目状态 + 上次采取的操作
- 人工做出的覆盖循环的决策

## 循环运行方式（典型周期）

1. 调度器触发（早晨或按间隔）。
2. 分类技能摄取：CI 失败（24 小时内）、开放的 Issue/工单、最近的提交、之前的 `STATE.md`。
3. 高优先级项目附加到状态中，并附上建议的下一步操作。
4. （第二阶段）对于小型、独立的失败：打开工作树 → 实施者 → 验证者。
5. （第三阶段）连接器更新 PR/工单；模糊项目标记为需要人工处理。
6. 从状态中清除已解决/已合并的项目。
7. 在状态中记录运行后评估：误报、重复项目、重新排序或丢弃的项目，以及为下次运行所做的一项调整。

## 运行后评估

每次每日分类运行后，记录：

- 高噪音项目。
- 误报（被错误标记的项目）。
- 应降低优先级的项目。
- 任何人工审查摩擦。
- 一项用于改进下一周期的变更。

## 验证策略

- 第一阶段（仅报告）：人工阅读 `STATE.md` — 无需验证自动操作。
- 第二阶段及以后：绝不允许实施者标记工作完成；验证者确认修复范围和测试。
- 分类技能不得虚构架构性工作 — 仅提供信号。

## 人工交接点

- 设计决策或多文件重构
- 安全、认证、支付、基础设施
- 分类输出中标记为“需要讨论”的项目
- 循环已提出 3 天以上仍未解决的事项

## 工具特定说明

**Grok Build TUI**：
```bash
/loop 1d 运行 loop-triage 技能。将高优先级项目附加到 STATE.md。仅限明显的小型 bug 修复：worktree + minimal-fix + verifier 子代理（制造者/检查者）。将模糊项目标记为需要人工审查。
```

**Claude Code**：
```bash
/loop 1d 运行 $loop-triage 并更新 STATE.md。第一周不要自动修复 — 仅报告。
```

**Codex**：
- 自动化选项卡：每日提示调用 `$loop-triage`，输出到 Triage 收件箱 + `STATE.md`。

**GitHub Actions**：
- 参见 `examples/github-actions/daily-triage.yml`。

## 故障模式与缓解措施

| 故障 | 缓解措施 |
|---------|------------|
| 分类产生噪音 | 收紧技能规则；添加“噪音 / 忽略”部分 |
| 状态文件无限增长 | 每次运行清除已合并/已关闭的项目 |
| 错误优先级的自动修复 | 从仅报告开始；添加明确的努力/风险门槛 |
| 错过隔夜故障 | 添加 `fireImmediately: true` 或在一天开始时 + 中午运行 |
| 评估过时 / 从未审查 | 当评估条目在 N 次运行中累积且未解决时，添加人工交接。 |

## 成本概况

| 场景 | 每次运行 Tokens | 备注 |
|----------|------------|-------|
| 无操作 | ~5k | 状态中无可操作事项 |
| 完整分类（L1） | ~50k | CI + Issue + 提交扫描 |
| 辅助修复（L2） | ~200k | 工作树 + 实施者 + 验证者 |

**节奏**：1d–2h · **层级**：低 · **建议每日上限**：100k tokens

```bash
npx @cobusgreyling/loop-cost --pattern daily-triage --cadence 1d --level L1
```

使用 `loop-init` 生成 `loop-budget.md` 和 `loop-run-log.md` 脚手架。参见 [operating-loops.md](../docs/operating-loops.md)。

## 成功指标

- 从“出现问题”到“人工知晓”的时间
- `STATE.md` 与手动检查结果一致的早晨百分比
- 临时“现在什么在冒烟？”Slack 消息的减少

从仅报告模式开始。只有当分类质量持续良好时，才添加自动操作。
