# CI 清扫循环

**目标**：快速响应主分支或活跃分支上失败的 CI — 诊断、提出最小修复方案，并在循环无法可靠解决时升级处理。

## 调度

**推荐**：
- 活跃开发期间使用 `/loop 15m`（Grok、Claude Code）
- 主分支变红且正在发布时使用 `/loop 5m`
- 在 `workflow_run` 失败时触发 GitHub Action（事件驱动，非轮询）

无人值守时，较慢的夜间节奏（30–60 分钟）也可以接受。

## 所需技能

- `ci-triage` — 解析 CI 日志，识别失败的作业/步骤，分类失败类型（不稳定测试、回归、环境、配置）
- `minimal-fix` — 针对特定失败的最小变更
- `loop-guard` — 熔断器：将每次尝试记录到 `loop-ledger.json`，重试前运行 `loop-context --check`；遇到相同失败时升级处理而非循环重试
- 项目测试/代码检查技能 — 针对你的技术栈的构建和测试命令

## 状态

`ci-sweeper-state.md` 或 `STATE.md` 中的章节：

```markdown
## CI 清扫 — 活跃失败

上次运行：2026-06-09 14:30 UTC

### main @ abc1234
- 作业：test-auth
- 失败：test_refresh_token_expiry 中的 AssertionError
- 尝试次数：1/3
- 上次操作：在 worktree fix/ci-auth-refresh 中提出最小修复
- 状态：等待验证器和人工确认

### 已解决（最近 7 天）
- main @ def5678 — 通过 PR #1250 合并了代码检查修复
```

跟踪：提交 SHA、失败作业、尝试次数、worktree/PR 链接、结果。

## 循环运行方式（典型周期）

1. 发现受监控分支（main、release/*、活跃 PR）上的 CI 失败。
2. 对于每个新失败：
   - 分类：不稳定测试 vs 真实回归 vs 基础设施问题。
   - 如果是不稳定测试（之前见过、间歇性出现）：加入观察列表，不自动修复。
   - 如果可处理：打开 worktree → 实现者起草修复方案。
3. 验证器子代理检查：修复是否解决失败、无无关变更、本地测试通过。
4. 打开 PR 或在现有 PR 上评论，附上建议修复。
5. 每次重试前，`loop-guard` 运行熔断器（`loop-context --check`）。如果相同失败重复出现 N 次或尝试次数超过上限（例如 3 次），则触发熔断：使用精简的上下文摘要升级给人工处理，而不是继续循环。
6. 从活跃列表中移除已解决的失败。

## 验证策略

- 验证器必须在批准前在 worktree 中运行测试。
- 实现者不能合并 — 只能提出建议。
- 不稳定测试检测：如果同一测试在无代码变更的情况下重试后从失败变为通过，则不自动修复。

## 人工交接点

- 基础设施故障（运行器内存不足、镜像仓库宕机、密钥缺失）
- 涉及超过 5 个文件或核心架构的失败
- 安全敏感的测试失败
- 同一失败超过最大尝试次数
- 需要隔离而非代码变更的间歇性不稳定测试

## 工具特定说明

**Grok Build TUI**：
```bash
/loop 15m 检查 main 和打开的 PR 上的 CI。对于新失败：分类，如果可处理则在 worktree 中起草最小修复并由验证器确认。更新 ci-sweeper-state.md。3 次尝试后升级处理。
```

**Claude Code**：
```bash
/goal main 上的所有测试通过且代码检查干净
```
使用 `/goal` 进行聚焦的"恢复绿色"会话；使用定时清扫器进行持续监控。

**Codex**：
- 自动化："每 30 分钟总结 CI 失败" → 分类收件箱；单独的自动化用于修复尝试。

**GitHub Actions**：
- 参见 `examples/github-actions/ci-sweeper.yml` — 在工作流失败时触发。

## 失败模式与缓解措施

| 失败 | 缓解措施 |
|---------|------------|
| 修复症状的循环 | 验证器检查根本原因，而不仅仅是 CI 变绿 |
| 用重试对抗不稳定测试 | 分类不稳定测试；隔离或跳过并创建工单 |
| 主分支变红时消耗过多 token | 在 N 次失败后暂停循环；批量修复 |
| 目标分支错误 | 在技能中明确设置分支白名单 |

## 成本概况

| 场景 | 每次运行 token 数 | 备注 |
|----------|------------|-------|
| 无操作（CI 绿色） | ~5k | **必需** — CI 绿色时不要运行完整清扫器 |
| 分类 / 归类 | ~50k | 日志解析 + 失败分类 |
| 修复尝试（L2） | ~200k | Worktree + 实现者 + 验证器 |

**节奏**：5 分钟–15 分钟 · **级别**：非常高 · **建议每日上限**：100 万 token · **需要提前退出**

```bash
npx @cobusgreyling/loop-cost --pattern ci-sweeper --cadence 15m --level L2
```

在 15 分钟节奏且无提前退出的情况下，最坏情况消耗超过每天 500 万 token。切勿在每次触发时运行完整的操作路径。

## 成功指标

- CI 变红后到首次提出修复方案的平均时间
- 无需人工干预即可解决的失败百分比（仅限简单情况）
- 重复失败率（同一作业在 48 小时内再次失败）

对于刚接触循环工程的团队来说，这是最佳入门循环 — 高频率、范围有限、验证清晰。
