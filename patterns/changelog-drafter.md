# 变更日志起草循环

**目标**：扫描自上次发布（或按固定节奏）以来的合并 PR、提交和标签，生成高质量、分类清晰的发布说明或 CHANGELOG 条目草稿。在笔记发布或版本发布之前，需由人工审核并批准。

## 调度

**推荐**：
- 活跃项目使用 `/loop 1d`（早晨或一天结束时）
- 发布准备时：手动触发或通过标签 Webhook / GitHub Action（`on: [release, workflow_dispatch]`）触发
- 节奏较慢的项目每周运行一次

这是一个极佳的“非高峰”或“冲刺结束”循环。与 CI 或 PR 守护循环相比，紧迫性较低。

## 所需技能

- `changelog-scan` — 发现最近的合并/PR/提交，提取标题、标签、关联 Issue 和破坏性变更信号。生成结构化列表。
- `draft-release-notes` — 将扫描到的项目 + 项目约定转化为简洁、面向用户的发布说明（分类：功能、修复、破坏性变更、安全、文档等）。
- `loop-verifier`（或人工审核）— 检查草稿的准确性、语气、完整性和对项目风格的遵循。绝不能让起草者自行评估其输出。

## 状态

文件名：`changelog-drafter-state.md`

已扫描内容和待审核草稿的紧凑记录：

```markdown
# 变更日志起草状态

上次运行：2026-06-09 18:30 UTC
上次发布：v2.14.0（标签 2026-06-01）

## 待审核草稿
- v2.15.0-rc（未发布）
  已扫描项目：17 个 PR + 4 个直接提交
  草稿位置：RELEASE_NOTES_DRAFT.md（或 PR 描述）
  状态：待人工审核

## 最近发布
- v2.14.0 — 发布于 2026-06-01（由 @cobus 审核）
```

一旦版本被标记/发布且草稿已合并，循环应清理相应条目。

## 循环运行方式（典型周期）

1. 确定“自何时起”的时间窗口（上次标签、状态中的上次运行日期，或最近 N 天）。
2. `changelog-scan` 列出合并到主分支的 PR 和值得关注的直接提交。提取约定式提交类型、标签（例如 `breaking`、`security`）、关联 Issue。
3. 将项目分组到标准章节（功能、Bug 修复、性能、破坏性变更、安全、文档、内部/杂务）。
4. `draft-release-notes` 撰写一份精美的 Markdown 草稿（包含链接、对贡献者的致谢、明显的升级说明）。
5. 验证器（或人工）审核草稿的以下方面：
   - 准确性（无虚构功能）
   - 完整性（高影响项目未被遗漏）
   - 语气和项目风格
6. 批准后：循环可以打开一个 PR 来更新 `CHANGELOG.md`（或 GitHub 发布说明），或者将草稿保留在文件中供维护者复制。
7. 在状态中记录运行情况并将项目标记为“已发布”。清理旧条目。
8. 在状态中记录运行后评审：遗漏项目、误报、分组问题、重试次数以及下次运行的提示/策略调整。

## 运行后评审

在人工审核草稿后，人工审核者或操作员记录上次运行遗漏或错误分类的内容，以便下次运行改进。这将捕获上次草稿运行中的审核发现。

在状态中的 `## 运行后评审` 标题下记录：

- **遗漏项目** — 用户报告的草稿中遗漏的变更
- **误报** — 草稿中不应面向用户的项目（杂务、仅基础设施相关）
- **分组问题** — 项目被分到错误章节（例如，修复被放在功能中）
- **重试次数** — 草稿被修订或重新生成的次数（+ 原因）
- **提示/策略调整** — 对扫描、起草或验证器技能指令的 1–2 项具体更改，用于下次运行

在 L1 自用测试运行期间可选但推荐。即使是偶尔的评审条目也有助于防止重复问题。

## 验证策略

- 起草者从不发布。它只提出建议。
- 独立的验证器技能（或人工）必须批准草稿。
- 对于自动更新 CHANGELOG 的 PR：PR 必须通过项目正常的审核门禁（或明确允许此循环）。
- 在最初几次运行以及任何包含破坏性变更的发布中，优先进行人工审核。

## 人工交接点

- 任何破坏性变更或安全说明
- 主版本号升级
- 需要大量营销/外部沟通的发布
- 循环生成的草稿在 N 天后仍未经过人工审核
- 扫描窗口包含超过约 50 个项目时（对单个发布来说太多 — 需拆分或人工策展）

## 工具特定说明

**Grok Build TUI**：
```bash
/loop 1d 对自上次标签或上次状态日期以来的合并运行 changelog-scan。使用 draft-release-notes 在 RELEASE_NOTES_DRAFT.md 中生成分类草稿。更新 changelog-drafter-state.md。未经人工批准不得提交/发布。
```

**Claude Code**：
```bash
/loop 1d 扫描最近的合并并起草发布说明。将草稿写入 RELEASE_NOTES_DRAFT.md + 更新状态。标记破坏性/安全项目以供审核。
```

**Codex**：
- 自动化：每日“变更日志起草者”，调用扫描 + 起草技能，并将草稿发布到分类收件箱或专门的发布准备 Issue 中。

**GitHub Actions**：
- 参见 `examples/github-actions/`，获取可在推送到主分支或 `workflow_dispatch` 时触发的工作流。它可以将草稿评论到发布跟踪 Issue 中，或创建草稿 PR。

## 失败模式与缓解措施

| 失败 | 缓解措施 |
|---------|------------|
| 虚构功能或错误归属 | 验证器将每个项目与实际 PR 标题 + 提交消息进行交叉核对。状态跟踪来源 PR。 |
| 遗漏重要变更 | 同时扫描主分支上的 PR *和*直接提交。使用标签 + 约定式提交。 |
| 笔记过长/过于嘈杂 | 在起草技能中严格执行分类 + “仅面向用户”规则。人工可进行删减。 |
| 与项目语气不匹配 | 在 AGENTS.md 或项目技能中提供简短的“发布语气”部分，供起草者阅读。 |
| 意外发布 | 未经明确的人工门禁 + PR，绝不授予循环对标签或实时 CHANGELOG 的写入权限。 |
| 评审过时/从未审核 | 当评审条目在多次运行（例如 3 次）中积累且未解决时，添加人工交接。 |

## 成本概况

| 场景 | 每次运行 Token 数 | 说明 |
|----------|------------|-------|
| 无操作（无新合并） | ~5k | 自上次标签以来无新内容时退出 |
| 扫描 + 分类 | ~35k | PR/提交扫描 |
| 起草 + 验证 | ~80k | 分类发布说明草稿 |

**节奏**：1d · **层级**：低 · **建议每日上限**：100k token

这是最便宜且高价值的循环之一。可安全地与其他循环并行运行。

## 成功指标

- 从“最后一次合并”到“发布说明发布”的时间（目标：补丁发布 < 1 天）
- 首次发布即包含说明的发布百分比（不再出现“我们又忘了更新变更日志”）
- 每次发布的人工审核时间（在循环学会项目语气后应下降）
- 用户发现的笔记中缺失的“意外”项目数量（目标：接近零）

这是 ROI 最高、风险最低的循环之一。非常适合作为 Daily Triage 稳定后的第二个或第三个循环。它直接改善每位用户和贡献者的体验。
