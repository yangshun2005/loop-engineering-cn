# Issue 分类循环

**目标**：持续发现、去重、确定优先级，并为新提交的 Issue、功能请求和讨论添加标签，确保团队（及其他循环）始终拥有一个干净、可操作的最优先队列。第一周为纯报告/提案模式。风险极低，杠杆效应高。

## 调度

**推荐方案**：
- `/loop 2h` 或 `1d`（对于活跃仓库，建议早晚各一次）
- 在 `issues` / `discussion` 事件上配置 GitHub Action，并设置定时回退任务
- 与每日分类完美配合（此循环为“我该做什么”报告提供输入）

这是一个非常适合常驻运行的低成本辅助循环。

## 所需技能

- `issue-triage` — 扫描开放的 Issue、讨论，以及（可选，通过 MCP）Linear / Jira。执行去重、提取信号（标签、评论、关联的 PR、时长、反应），并建议优先级、推荐标签和一句话摘要。
- `loop-verifier`（轻量级或人工）— 在应用任何建议的分类操作或新标签之前，对提议进行合理性检查。

## 状态

文件名：`issue-triage-state.md`

当前待办队列健康状况的紧凑滚动视图：

```markdown
# Issue 分类状态
上次运行：2026-06-09 09:15 UTC
开放可操作项：14（之前为 17）
自上次运行以来新增：3
需人工处理：2（一个可能是 #412 的重复项，一个规格不明确）

## 前 5 项（按循环评分）
- #487（缺陷，p1，2 天前）— “导出大文件时崩溃” — 建议：缺陷 + 需复现 + 区域：导出
- ...
```

该循环会清除已关闭/已合并的项目，仅保留“需要关注”的项目。

## 循环运行方式（典型周期）

1. 发现自上次运行以来新增/更新的 Issue 和讨论（首次运行则为所有开放项）。
2. 对每项：总结意图，检测重复项（标题 + 嵌入提示或简单文本匹配），提取信号（时长、作者、关联的 PR、反应、现有标签）。
3. 评分/分桶：P0（安全、生产故障）、P1（高影响 + 明确）、P2、P3、需补充信息、重复项。
4. 将更新后的清晰优先级列表 + 建议标签集 + 简短的“重要性说明”写入状态文件（可选地，在 Issue 本身上添加“循环分类备注”评论）。
5. 验证器（或人工）仅审查“需人工处理”桶以及敏感区域上任何建议的标签变更。
6. 记录运行情况，清除已解决项目，更新计数。

## 验证策略

- 该循环在 L1 阶段**绝不会自动添加标签或关闭** Issue。
- 在 L2 阶段，仅在验证器通过后，可应用白名单标签（例如 `area:*`、`needs-repro`）。
- 在最初几周，涉及认证、支付、安全或公共 API 的任何事项，P0/P1 的分配始终由人工负责。

## 人工交接点

- 任何涉及安全、认证、计费或基础设施的 Issue
- 不确定的重复检测（错误概率 > 30%）
- 循环想要作为“过期”关闭的超过 N 天的 Issue（需人工确认）
- 单次运行中出现超过 X 个新 Issue（上下文过载信号）

## 工具特定说明

**Grok Build TUI**：
```
/loop 2h 运行 issue-triage 技能。首先读取 issue-triage-state.md。仅针对新项目生成更新后的状态和建议标签。不自动添加标签或关闭。任何模糊事项均升级处理。
```

**Claude Code**：
```
/loop 2h $issue-triage — 更新 issue-triage-state.md。仅对白名单区域提议标签。P0/P1 需人工审查。
```

**Codex**：
每 2 小时或 `issues` 事件触发时自动运行：执行 issue-triage → 更新状态。报告模式。

**GitHub Actions**：
参见 `examples/github-actions/` 获取入门工作流，可响应 Issue 事件并支持定时运行。

## 故障模式与缓解措施

| 故障模式                  | 缓解措施 |
|--------------------------|----------|
| 过度优先处理嘈杂的报告者 | 根据团队真正关心的信号（反应、关联的 PR、内部 +1）加权。人工覆盖记录在状态中。 |
| 重复项误报 | 保守匹配 + 在 L1 阶段始终将“可能为 #NNN 的重复项”提交人工确认。 |
| 每个新 Issue 都触发警报疲劳 | 仅对“需人工处理”部分通知人工。其余内容均保存在状态文件中，供每日分类或工程师阅读。 |

## 成功指标

- Issue 从打开到获得首个有效标签或“需补充信息”评论的时间缩短。
- 24 小时内具有明确优先级的 Issue 百分比。
- 工程师反馈的“我总是知道前 5 项是什么”评分（定性，来自状态文件审查）。
- 在两个人开始处理同一重复项之前捕获的重复数量。
